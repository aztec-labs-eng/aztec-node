## Overview

**Migration difficulty**: high. Two things make this unlike a v5 point release.

Configuration must be changed **before** you upgrade. The `ACVM_*` variables are renamed with no
fallback, and a node that still sets only the old names fails to start rather than running degraded.

The protocol changed, so v5 and v6 nodes do **not** interoperate and nodes resync their archiver on
first start. Plan a coordinated upgrade with time for the resync, not a rolling one.

## Behaviour changes

### `ACVM_*` configuration renamed to `NOIR_EXECUTE_*`

Protocol circuits are now executed with noir's `noir-execute` rather than the `acvm` binary, and the
configuration naming the executor follows the tool. What you point it at is unchanged.

| Old | New |
| --- | --- |
| `ACVM_BINARY_PATH` | `NOIR_EXECUTE_BINARY_PATH` |
| `ACVM_WORKING_DIRECTORY` | `NOIR_EXECUTE_WORKING_DIRECTORY` |
| `--sequencer.acvmBinaryPath` | `--sequencer.noirExecuteBinaryPath` |
| `--sequencer.acvmWorkingDirectory` | `--sequencer.noirExecuteWorkingDirectory` |
| `--proverNode.acvmBinaryPath` | `--proverNode.noirExecuteBinaryPath` |
| `--proverNode.acvmWorkingDirectory` | `--proverNode.noirExecuteWorkingDirectory` |

```diff
- ACVM_BINARY_PATH=/usr/src/labs-aztec-toolchain/bin/noir-execute
- ACVM_WORKING_DIRECTORY=/usr/src/acvm
+ NOIR_EXECUTE_BINARY_PATH=/usr/src/labs-aztec-toolchain/bin/noir-execute
+ NOIR_EXECUTE_WORKING_DIRECTORY=/usr/src/noir-execute
```

**There is no fallback to the old names.** A prover agent exits with `Requested real proving but no
path to bb or noir-execute binaries provided`; a prover node or sequencer configured for real proofs
throws from `BBNativeRollupProver.new` when it tries to stat an undefined path. Only a node running
without real proofs survives, by falling back to WASM simulation — which is much slower, so a node
that appears to start may still be badly degraded.

If you run the release image it sets the new variables itself, and its default working directory moves
from `/usr/src/acvm` to `/usr/src/noir-execute`. Check any values you override.

### Block headers commit to a per-block tx effects tree

The L2 block header gains a `tx_effects_tree_root`: the root of a per-block merkle tree with one leaf
per transaction, binding each transaction hash to a structured hash of its effects. Holding a block
header is now enough to verify a transaction's inclusion and effects with a short membership proof,
rather than replaying the checkpoint's full sponge blob.

This is a breaking protocol change, and the consequences for an operator are:

- **Nodes resync their archiver** on first v6 start. The archiver data schema moves 9 → 10, and it now
  also stores each block's tx effects tree leaves. Budget for the resync.
- **v5 and v6 nodes do not interoperate.** Block header serialization grew a field, so transaction
  hashes, verification keys, contract artifacts, canonical contract addresses and the genesis
  constants all change.
- **PXE databases are re-initialized** on next open (data schema 14 → 15). The PXE oracle interface
  version moves 30 → 31 and TXE 8 → 9.
- Contracts must be recompiled against the updated `aztec-nr`. That is a developer concern rather than
  an operator one, but it is why a v6 network cannot serve v5-compiled contracts.

### Attester-signed withdrawals

Two commands let a withdrawal be signed by the position's attester rather than the withdrawer:

```bash
aztec initiate-withdraw-by-attester          # one position
aztec initiate-withdraw-by-attester-batch    # several
```

Both take `--l1-rpc-urls` / `ETHEREUM_HOSTS`, `--l1-chain-id` / `L1_CHAIN_ID`, and the attester key as
`--private-key` or `--mnemonic`. Existing withdrawer-signed flows are unchanged.

### `MultiCallEntrypoint`, `HandshakeRegistry` and `AuthRegistry` re-pinned

These canonical contracts are deployed at new addresses in v6. If you hold any of them in configuration
or monitoring, take the current values from [networks.md](/networks) rather than carrying them forward.

## New node RPC methods

Two additions to the JSON-RPC surface. Both are additive; nothing was removed.

| Method | What it is for |
| --- | --- |
| `aztec_getTxEffectMembershipWitness` | Membership proof for a transaction's effects against the new tx effects tree. |
| `aztec_getValidatorStatsBatch` | Validator statistics for several attesters in one call. |

Both currently render under "Other methods" in the [node API reference](/operate/operators/reference/node-api-reference)
because the generator has no grouping for them yet.

## Upgrade checklist

1. Rename `ACVM_*` to `NOIR_EXECUTE_*` in your environment, compose files or Helm values, **before**
   starting a v6 node.
2. Confirm any overridden working directory matches the new default if you rely on the release image.
3. Plan for an archiver resync on first start, and for v5 and v6 nodes being unable to serve each
   other during the upgrade.
4. Re-read canonical contract addresses from [networks.md](/networks).
5. Start a single node first and confirm it syncs before rolling the rest of a fleet.
