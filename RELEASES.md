## Releases

Releases are driven by git tags. Each branch's version is tracked in its `.release-please-manifest.json` at the project root. Tags are created exclusively by the [release tag workflow](./.github/workflows/release-tag.yml) and the [release PR workflow](./.github/workflows/release-pr-tag.yml), both through the release GitHub App — a ruleset blocks anyone else (admins included) from creating `v*` tags. Nightly tags (`v<ver>-nightly.<date>`) are cut every night for each branch in the workflow's matrix. A manual dispatch with `kind=nightly` cuts one on demand, for a day the cron missed or botched; it takes an optional `suffix` (`v<ver>-nightly.<date>.<suffix>`, 1-20 lowercase letters and digits starting with a letter) so a re-cut does not collide with a tag the cron already pushed. A re-cut is released like any nightly and takes the nightly aliases from the day's scheduled build; since suffixes are words rather than a sequence, two re-cuts on one day have no meaningful order between them. The suffix is its own prerelease identifier, so the release channel stays `nightly` and the tag sorts after the day's scheduled one. Scheduled runs never carry a suffix, so the plain date tag remains what scheduled consumers resolve. A release candidate (`v<ver>-rc.<n>`, with `n` auto-incremented from origin's existing rc tags) is a manual dispatch with `kind=rc`; a real release (`v<ver>`) is a manual dispatch with `kind=stable`. Every dispatch pauses for a second person's approval, a nightly re-cut included; the cron is the only unattended path. No dispatch ever moves an existing tag: a run whose tag is already on origin fails instead of retagging. A new tag triggers the [release workflow](./.github/workflows/release.yml), which runs `./bootstrap.sh release` to build and publish the version at that tag: the aztec-nr crates as a tagged snapshot on the [aztec-nr mirror](https://github.com/aztec-labs-eng/aztec-nr) (which `aztec init` pins), docker images to DockerHub, and the aztec-up and playground assets to S3. The npm packages are only packed by that build (`ci3/deploy_npm` in pack mode, into a bundle keyed by the tag in the build cache); the workflow's `publish-npm` job then publishes the bundle from a GitHub runner with [npm trusted publishing](https://docs.npmjs.com/trusted-publishers/) (`ci3/publish_npm_release`), so no machine that runs the built tree holds npm credentials and there is no npm token in the repository. Each `@aztec-labs` package's trusted publisher on npmjs names this repository and `release.yml`. The `ci-release-pr` label on a pull request cuts a canary release the same way: `v<ver>-commit.g<sha>` at the PR head, released like any other tag, with the `commit` channel keeping it off the shared npm dist-tags.

A *private release* publishes the same version to the Labs-owned GCP Artifact Registry instead, and publishes nothing public. It is a manual dispatch of the release tag workflow with `kind=private`, gated by the same second-person approval as an rc, which cuts the tag `private/v<ver>-private.<n>`. That tag triggers the [private release workflow](./.github/workflows/private-release.yml), which runs the same `./bootstrap.sh release` under `RELEASE_TARGET=private`: the `@aztec-foundation` packages it builds against and the `@aztec-labs` packages it publishes both come from and go to the Artifact Registry npm repo, and the docker images go to the Artifact Registry docker repo. The `private/` prefix is part of the ref, not the version: it is what routes the tag to this workflow and to the `release-private` environment, which holds the Artifact Registry credential and nothing that can publish publicly — while the `release` environment holds the DockerHub credentials and nothing that can read the Artifact Registry (npmjs takes no credential; see above). A job declares one environment, so no run can read from one side and publish to the other. Private releases skip `aztec-up` and `playground`, whose artifacts are public by nature, and upload nothing to the build cache, which is world-readable.
